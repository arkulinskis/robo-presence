Build the robot

A Robo Presence robot is a camera on a pan-tilt head, riding on two motors, with a computer that streams the video and moves the parts. Everything else is optional.

PartWhat to getNotes
BrainRaspberry Pi 4 or 5 (2 GB is plenty)A Pi Zero 2 W works at 320 × 240. A Pi 3B+ at 640 × 480, 15 fps.
CameraCamera Module 3 (or 2), or any USB webcamThe Pi camera is lighter on the CPU. Wide-angle versions feel better to drive.
ChassisA 2WD or 4WD kit, or tank tracks, with two DC gear motorsFour motors? Wire each side's pair together.
Motor driverTB6612FNG (recommended), L298N or DRV8833The TB6612 runs cooler and wastes less battery than the L298N.
HeadTwo SG90 or MG90S servos + a pan-tilt bracketOr a pan-tilt HAT with a PCA9685 chip (steadier servos, uses I²C).
Power2S Li-ion pack (7.4 V) + a 5 V 3 A step-down (UBEC) for the PiServos want their own 5 to 6 V supply, not the Pi's 5 V pin.
ExtrasArduino Nano/Uno, HC-SR04 sonar, LEDs, a buzzer, a USB speakerAnything else: see New parts.

Power, the part people get wrong

  • Feed the Pi from a 5 V regulator that gives at least 3 A. When motors start they pull the battery voltage down; a weak supply reboots the Pi mid-drive.
  • Give the motors their power from the battery through the motor driver (VM / 12V pin), and the servos their own 5 to 6 V.
  • Join every ground: the Pi, the motor driver, the servo supply and the Arduino share GND, or signals won't work.
  • The Pi's pins are 3.3 V. An HC-SR04 echo pin gives 5 V: put a 1 kΩ + 2 kΩ divider in between.

Wiring

Every robot's Parts tab draws its own wiring: a map of the Pi's 40-pin header with each used pin marked, and a list of what goes where. The Raspberry Pi starting set uses:

Wheels (TB6612)left IN1/IN2/PWM = GPIO 17/27/12, right = 23/24/13, STBY = 25
Pan / tilt servosGPIO 18 / GPIO 19
HeadlightsGPIO 16 (through a transistor or LED driver for anything bright)
BuzzerGPIO 26
Sonartrigger GPIO 5, echo GPIO 6 (divider!)

Set up the Raspberry Pi

  1. Install Raspberry Pi Imager on a computer.
  2. Choose your Pi model and Raspberry Pi OS Lite (64-bit) (Bookworm or newer). The desktop version works too, it just uses more memory.
  3. In the settings ("Edit settings"), set a host name (e.g. sprocket), a user name and password, your Wi-Fi, and turn on SSH.
  4. Write the card, put it in the Pi, power it up and give it a minute.
  5. From a computer on the same Wi-Fi:
    ssh <user>@sprocket.local

Using a pan-tilt HAT (PCA9685)? Turn on I²C: sudo raspi-config → Interface options → I2C.

Install the robot code

Make a robot in your garage, open its Install tab and copy the one-line command. On the Pi:

curl -fsSL 'https://<this app>/_/api/install?c=ABCD2345' | sudo bash

It takes a few minutes the first time. It:

  • installs system packages (picamera2, gpiozero, lgpio, pyserial, smbus2, espeak-ng; pigpio on a Pi 4 and older),
  • makes a Python environment in /opt/robopresence/venv with aiortc (WebRTC for Python),
  • downloads the robot code from GitHub to /opt/robopresence/robot,
  • trades the one-time code for the robot's own secret token (kept in /etc/robopresence/robot.json, readable only by you),
  • starts the robopresence service, which starts again by itself after a reboot.

The Install tab turns green when the robot calls in. Handy commands on the robot:

robopresence statusis it running?
robopresence logsfollow its log (Ctrl+C to leave)
robopresence testsweep servos, flash switches, read sensors
robopresence test --wheels…and spin the wheels (lift the robot!)
robopresence updateget the newest robot code, keep the pairing
robopresence pair ABCD-2345pair again with a new code
robopresence infoshow the pairing and the parts it reports

Prefer to read first? The installer is robot/install.sh. To install by hand: download the robot folder and run sudo bash install.sh --server https://<this app>/_/api --code ABCD-2345.

No Pi? Robot mode runs the robot in a browser tab on an old phone or laptop: open the robot and press Run it in this browser.

Add an Arduino

Choose the Raspberry Pi + Arduino brain when you'd rather let an Arduino (Uno, Nano, Mega…) drive the motors, servos and sensors: it has steadier timing, 5 V pins and analog inputs for a battery. The Pi still streams the video and talks to the cockpit; it sends the Arduino one-line commands over USB.

  1. In the Parts tab, set the parts' Runs on to Arduino and choose Arduino pins (2 to 13, A0 to A7).
  2. The Install tab shows the robopresence_bridge sketch with its CONFIG block filled in. Copy it into the Arduino IDE, pick the board and port, Upload.
  3. Plug the Arduino into the Pi's USB. On start, the Pi asks the Arduino ? and it lists its parts.
On an Uno or Nano the Servo library takes over PWM on pins 9 and 10, so put motor speed pins on 3, 5, 6 or 11.

The Arduino stops the wheels by itself 700 ms after the last command, a second safety net under the Pi's own watchdog.

New parts (more actuators later)

Nothing in the cockpit is hard-coded. When the robot starts (and whenever its parts change) it sends a manifest: the list of parts that actually work. The cockpit turns each part into a control:

Three ways to add a part

  1. A standard part: add it in the Parts tab and save. The robot picks up the new config within a couple of seconds, rebuilds its parts and sends the new manifest; the cockpit redraws, even mid-drive.
  2. A Python plugin for hardware the robot code doesn't know: put a file in /etc/robopresence/plugins/ on the robot and add a Plugin part naming it. A claw on a servo:
    # /etc/robopresence/plugins/my_claw.py
from robopresence import parts as P

class Claw(P.Positioner):          # a value that moves smoothly to its target
    UNIT = "%"
    def start(self):
        from gpiozero import AngularServo
        self.servo = AngularServo(22, min_angle=0, max_angle=180)
    def write(self, v):             # 0 % open .. 100 % closed
        self.servo.angle = 10 + 85 * v / 100

def make(spec, robot):
    return Claw(dict(spec, min=0, max=100, home=0), robot)
    Other bases: Switch (override write(on)), Sensor (override read()), or Part for anything. The example lives in robot/plugins/example_claw.py.
  3. Let the Arduino report it: add a line to the sketch's CONFIG lists (a servo, slider, switch or analog). The Arduino announces it on start; parts the config doesn't have are added automatically and appear in the cockpit.

How the connection works

  1. The robot checks in with Robo Presence every second or two (faster while someone has its page open), over plain HTTPS. No ports to open on your router.
  2. When you press Drive, your browser makes a WebRTC offer (it wants video, and opens two data channels: one fast and lossy for the joystick, one reliable for everything else) and leaves it with the server.
  3. The robot picks it up, answers with its camera, and the server hands the answer back.
  4. From then on your browser and the robot talk directly. The server never sees the video or the controls.

Latency

The cockpit shows the round trip (RTT), the frame rate and whether the path is direct (P2P) or relayed. To make it snappier: use 5 GHz Wi-Fi, a lower camera size (Parts tab → Camera), and H.264 (lighter on the Pi). Joystick commands go 20 times a second on the lossy channel, so a lost packet is simply replaced by the next one instead of delaying it.

STUN and TURN

Both sides first ask a public STUN server (Google's, by default) for their public address. That finds a direct path on most home and mobile networks. Some strict networks block it; then the connection needs a TURN relay, a server that forwards the encrypted media. Admins add TURN servers (yours, or a hosted one) in Admin → Network, and both browsers and robots use them.

Protocol (for your own robot)

Anything that speaks this can be a Robo Presence robot: the Python robot, robot mode in a browser, or your own code (ESP32 with a companion, ROS bridge…).

Robot ↔ server (HTTPS, JSON)

POST /_/api/bot/claim{code, info} → {token, robot_id, name} (once, with the install code)
POST /_/api/bot/hello{token, manifest, info} → {config, config_rev, ice_servers, poll_ms}
POST /_/api/bot/poll{token, telemetry, sessions, config_rev, manifest?} → {offers, ended, config?, next_ms}
POST /_/api/bot/answer{token, session, sdp} or {token, session, reject}
POST /_/api/bot/event{token, kind, text}: a line in the robot's log on the website

A 401 reply means the robot was unpaired: stop and ask for a new code.

Cockpit ↔ robot (WebRTC data channels, JSON)

cockpit -> robot
  {"t":"hello"}                          robot replies with its manifest and state
  {"t":"drive","x":0.2,"y":0.8,"s":42}   x = turn, y = forward, -1..1; s = sequence number
  {"t":"set","id":"pan","v":30,"s":43}   servo / slider value, or true/false for a switch
  {"t":"press","id":"horn","down":true}  button down / up
  {"t":"say","id":"voice","text":"Hi"}
  {"t":"stop"}  {"t":"home"}  {"t":"seat"}  {"t":"ping","n":7,"ts":...}
robot -> cockpit
  {"t":"manifest", "controls":[...], "sensors":[...], "problems":[...]}
  {"t":"state","values":{"pan":30,...},"seat":{"driver":"..","name":"Ana"}}
  {"t":"tel","sensors":{"battery":7.6,...}}   once a second
  {"t":"pong",...}  {"t":"log","level":"stop","text":"Wheels stopped: no signal..."}

Rules every robot keeps: stop the wheels when no drive arrives for the watchdog time (500 ms), when the driver disconnects, and on stop. Ignore messages from viewers (except stop) and from anyone who isn't in the driver's seat. The full reference is in robot/robopresence/robot.py.

Troubleshooting

The robot stays offline

On the robot: robopresence status and robopresence logs. Check the Wi-Fi (ping -c3 google.com). If the log says "unpaired", make a new code in the Install tab and run robopresence pair CODE.

"The robot answered, but no direct connection could be made"

One of the networks blocks direct WebRTC. Try another network (a phone hotspot) to confirm, then add a TURN server in Admin → Network.

No picture, or "Camera: test pattern"

Pi camera: check the ribbon cable (contacts facing the right way) and run rpicam-hello. USB webcam: ls /dev/video*. Set the source explicitly in Parts → Camera.

The Pi reboots when the motors start

A brownout: the motors drag the supply down. Use a separate 5 V 3 A regulator for the Pi and a capacitor (470 µF) across the motor supply.

The servos jitter

On a Pi 4 and older the installer sets up pigpio for steady pulses; on a Pi 5, use a PCA9685 board. Give the servos their own 5 to 6 V supply and join the grounds.

It drives in circles / backwards

In the Parts tab: tick Reverse left/right motor, or swap the motor wires. A slow pull to one side: use Trim.

The Arduino parts say "not working"

Is the bridge sketch uploaded, and its CONFIG block the same as the Parts tab (ids must match)? ls /dev/ttyACM* /dev/ttyUSB* should show it.

Lag is high

Lower the camera size and frame rate, prefer H.264, move closer to the router or use 5 GHz, and check the cockpit says P2P rather than RELAY.
